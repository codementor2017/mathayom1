Testing and Debugging Simple Programs

Every program has bugs at first — even the ones written by professionals. In this lesson, you'll learn how to test your program with normal cases, boundary cases, and invalid inputs. You'll also learn how to find and fix common errors like a real programmer.

Warm-Up: Find the Bug

Look at this simple grade calculator program. There's a bug in it. Can you spot it?

🐛 Buggy Program
score = float(input("Enter score: "))

if score > 80:
    print("Grade: A")
elif score > 70:
    print("Grade: B")
elif score > 60:
    print("Grade: C")
else:
    print("Grade: F")

What's the problem? 🤔

Test it with score = 80. What grade does it print?

💡
The bug: When score = 80, the first check 80 > 80 is False, so it goes to the next check. It prints "Grade: B" — but 80 should be an A! The comparison should be >= (greater than or equal to), not >.
Why Test and Debug?

Testing means running your program with different inputs to see if it works correctly. Debugging means finding and fixing the errors that testing reveals.

🔍

Testing

Running the program with different inputs to check if the output is correct.

🐛

Bug

An error in a program that causes wrong results or crashes.

🔧

Debugging

Finding the bug and fixing it so the program works correctly.

✅

Improvement

Making the program better based on what you find during testing.

💡
Testing is not failure — it's part of the process! Professional programmers spend more time testing and debugging than writing code.

Three Kinds of Test Cases

A good programmer tests with three kinds of inputs. Let's use the grade calculator as an example:

Type of Test Purpose Example (Grade Calculator)
Normal Case A typical input the program should handle score = 75 → should print "B"
Boundary Case An input at the exact edge of a range score = 80 → should print "A" (not "B"!)
Invalid Case An input the program shouldn't accept score = -10 → should print an error
💡
Boundary cases are the trickiest! Bugs often hide at the exact edges — like when a score is exactly 80, or when a weight is exactly 0.
The Debugging Log

A debugging log is a table where you record each test — what you tried, what you expected, what actually happened, and how you fixed it.

Test Input Expected Actual Fix
Normal 75 B B None
Boundary 80 A B ❌ Change > to >=
Invalid -10 Error F ❌ Add validation
💡
Keep the log as you test. It helps you remember what worked, what didn't, and what you changed.

Common Bugs to Watch For

Here are the most common bugs in beginner programs:

🔢

Wrong Comparison

Using > when you need >=. Very common at boundaries!

🅰️

Assignment vs Comparison

Using = (assignment) when you should use == (comparison).

📦

Missing Variable

Using a variable you forgot to create, or misspelling its name.

🧮

Wrong Formula

Using the wrong operator (like + instead of ×), or missing parentheses.

🔢

Off-by-One Error

range(5) gives 0–4, not 1–5. Remember: Python stops before the last number!

❓

Missing Validation

Not checking for invalid inputs like negative numbers or zero.

Guided Practice: Test the Grade Calculator

Let's test the fixed version of the grade calculator together:

Fixed Program
score = float(input("Enter score: "))

if score < 0 or score > 100:
    print("Invalid score! Must be 0-100.")
elif score >= 80:
    print("Grade: A")
elif score >= 70:
    print("Grade: B")
elif score >= 60:
    print("Grade: C")
else:
    print("Grade: F")

Now let's test it with all three kinds of cases:

Test Input Expected Output Pass?
Normal 85 Grade: A ✅
Normal 75 Grade: B ✅
Boundary 80 Grade: A ✅
Boundary 60 Grade: C ✅
Boundary 59.9 Grade: F ✅
Invalid -10 Invalid score! ✅
Invalid 105 Invalid score! ✅
💡
Boundary test 80 → A. Before the fix, it printed B. This is exactly why we test boundary cases!

Key Takeaway

Testing finds bugs. Debugging fixes them. Test with three kinds of cases: normal, boundary, and invalid. Use a debugging log to record what you tried and what you fixed. Watch out for common bugs like wrong comparisons (> instead of >=), missing validation, and off-by-one errors. Remember: testing is not failure — it's how professionals make programs reliable.
